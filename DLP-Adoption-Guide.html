The Problem

Most data loss isn't caused by sophisticated attackers — it's caused by employees accidentally uploading sensitive files to personal cloud storage, pasting credit card numbers into chat apps, or emailing spreadsheets with PII to the wrong recipient. Without DLP, you have zero visibility into what data is leaving your environment.

The Opportunity

Zscaler DLP is already included in your platform. It inspects data inline as it moves through the Zscaler cloud — no additional hardware, no endpoint agents required for web/SaaS coverage. And you don't have to start by blocking anything. The most valuable first step is simply turning on visibility.

DLP Architecture

Three building blocks: Dictionaries define what to look for, Engines define the logic, Policies define who and what to do.

How They Connect: DLP Rules
In the admin portal, you create DLP Rules that tie everything together: select an Engine, define the scope (users, groups, departments, destinations), and assign an action (Allow, Caution, Block). Rules are evaluated in order — first match wins.
Detection Methods
Traditional Classification
Regex patterns and predefined dictionaries match known data formats — credit cards (Luhn checksum), SSNs, medical terms.
Exact Data Match (EDM)
Compares content against hashed reference values from your actual data (SSNs, account numbers). Eliminates false positives.

Indexed Document Match (IDM)
Fingerprints sensitive documents (contracts, IP). Detects full or partial matches in outbound traffic.

AI-Powered Classification
ML models detect sensitive data in unstructured content — faster and more accurate than regex for complex scenarios.
Policy Actions
👁️
Allow (Log Only)
Traffic passes through. Incident is logged. Zero user impact. This is your MVP starting point.
⚠️
Caution
User sees a warning page. They can acknowledge and proceed or cancel. Creates accountability without blocking.
🚫
Block
Transaction is blocked. User sees a notification. Use this only after tuning to minimize false positives.
Prerequisites

SSL inspection must be enabled for DLP to function. DLP cannot inspect what it cannot see. If traffic is bypassing SSL inspection, DLP is blind to that traffic. This is why the SSL Inspection Assessment should be completed before deploying DLP.

MVP DLP Program

You don't need a full data classification program, dedicated DLP analysts, or expensive add-on licenses to get started. Here's how to build a practical DLP program from zero.

The MVP Philosophy

Start with visibility (log only), not enforcement (block). Let the data tell you where the risks are. Tune policies based on real incidents. Graduate to enforcement only when you're confident in detection accuracy. This approach builds organizational buy-in because you're proving value before creating friction.

Phase 1
Monitor Only — See What's Happening
Weeks 1–2 • Zero user impact
Enable predefined DLP engines with Allow (log only) action. No user sees anything different. You get full visibility into sensitive data leaving your environment.
  • Enable the PCI engine (credit card numbers) — set action to Allow
  • Enable the PII engine (SSNs, names, addresses) — set action to Allow
  • Enable the HIPAA engine (medical information) — set action to Allow, especially relevant for healthcare orgs
  • Enable the Source Code engine — set action to Allow (catches developers uploading code)
  • Set confidence thresholds to High to minimize false positives
  • Configure DLP notification email to go to a designated security contact
What You'll Learn

"Within the first week, you'll see exactly what sensitive data is moving through your environment, who's sending it, and where it's going. This data is the foundation for every decision that follows."

Phase 2
Analyze & Tune — Understand the Patterns
Weeks 3–4 • Still zero user impact
Review the incidents generated in Phase 1. Identify false positives, top offenders, riskiest destinations, and legitimate business workflows that trigger DLP.
  • Review DLP incident logs: who, what data type, what destination, how often
  • Identify false positives — tune confidence thresholds or exclude specific destinations
  • Categorize incidents: accidental (training issue) vs. risky (policy issue) vs. malicious (investigation)
  • Identify the top 3–5 riskiest patterns (e.g., "Finance team uploading SSN-containing files to personal cloud")
  • Build a simple weekly report: incident count by type, top users, top destinations
Building the Business Case

"This report is your ammunition. 'Last month, we detected X instances of PII being uploaded to unsanctioned cloud storage. Here are the top destinations and users. Here's what we recommend.' That's how you go from monitoring to action with organizational support."

Phase 3
Caution — Educate Before You Enforce
Weeks 5–6 • Users see warning pages (can still proceed)
For the top 3–5 riskiest patterns identified in Phase 2, change the action from Allow to Caution. Users see a warning page and must acknowledge before proceeding. This creates accountability and awareness without blocking work.
  • Change action to Caution for high-risk patterns only (targeted, not blanket)
  • Customize the caution page with a clear explanation of why the action was flagged
  • Monitor: how many users proceed vs. cancel? Cancellations indicate awareness is working
  • Track helpdesk tickets — if they spike, your caution rules may be too broad
  • Continue Allow (log only) for everything else
Why Caution Before Block

"Caution pages are the most underrated DLP feature. They turn every potential incident into a training moment. The user learns in real time that their action involves sensitive data. Many organizations find that Caution alone reduces risky behavior by 40–60% — without ever blocking anything."

Phase 4
Enforce — Block Confirmed High-Risk Patterns
Weeks 7+ • Targeted blocking on validated rules only
For patterns that persist after Caution — users who consistently proceed through warnings — graduate to Block. Only block rules you're confident in after weeks of tuning.
  • Block rule examples: bulk credit card uploads to personal storage, SSN-containing files to unsanctioned apps
  • Keep Caution for gray-area scenarios where users may have legitimate justification
  • Keep Allow (log only) for broad monitoring and new patterns
  • Establish a quarterly review cadence: tune rules, review incidents, update policies
  • Present results to leadership: incidents detected, incidents prevented, risk reduction over time
The Long Game

"A mature DLP program uses all three actions simultaneously. Allow for broad visibility, Caution for education, Block for confirmed high-risk. This layered approach gives you maximum coverage with minimum business friction."

A Note on Incident Management

Without the Workflow Automation add-on, DLP incident alerts are delivered via SMTP email notifications. This means incidents go to an admin mailbox — there's no built-in ticketing, user justification workflows, or automated triage. This is functional for an MVP program, but it means someone needs to own that inbox and review incidents regularly.

For organizations that want to scale beyond the MVP: Workflow Automation adds incident assignment to end users for justification, integration with SIEM and GRC platforms, and automated remediation workflows. It transforms DLP from "alert and hope someone reads it" to a managed program. If your MVP data shows significant volume, Workflow Automation becomes the natural next investment.

Predefined DLP Engine Guide

Zscaler includes predefined engines for common compliance and data protection scenarios. Here's what to enable and when.

EngineDetectsPhaseNotes
PCI Credit card numbers (Luhn checksum validated) Start Here Low false positive rate due to Luhn validation. Set confidence to High, match count low (>1) for documents, medium for spreadsheets.
PII (US) SSNs, names, addresses Start Here Available in High Volume (>25 matches) and Low Volume (>1 match) variants. Start with High Volume to reduce false positives.
HIPAA Medical information + SSNs Start Here Combines Social Security Numbers and Medical Information dictionaries. Essential for healthcare organizations or any org handling PHI.
Source Code Programming patterns (class, void, import) Start Here Detects code being uploaded to unauthorized destinations. Minimum 1KB data size threshold. High value for protecting IP.
GLBA Financial statements + SSNs Phase 2 Gramm-Leach-Bliley Act compliance. Relevant for financial services organizations.
PIPEDA Canadian PII (SIN, credit cards, names) Phase 2 Available in High and Low Volume variants. Enable if you handle Canadian personal information.
Country-Specific PII Expanded PII dictionaries for various jurisdictions Phase 2 Recently expanded dictionaries covering international PII formats. Enable based on where you operate.
Offensive Language Adult content patterns Phase 3+ Uses Adult Content dictionary. Relevant for HR policy enforcement and K-12 environments.
Custom Engines Your specific data patterns Phase 3+ Build engines with your own keywords, regex, and dictionary combinations. "Project codenames," "internal classification labels," etc.
EDM (Exact Data Match) Hash-matched against your actual data Phase 3+ Upload hashed reference data (SSNs, account numbers). Near-zero false positive rate. Requires data preparation.
Tuning Tip: Confidence Scores

Every predefined dictionary has a configurable confidence score threshold (Low, Medium, High). Start with High confidence to minimize false positives. If you're not seeing enough detections, lower to Medium. Low confidence should only be used when you've validated the additional matches are genuine. False positives erode trust in the DLP program faster than anything else.

Get Started

Follow these steps to configure your MVP DLP program. Each step maps to the MVP phases described in this guide.

Step 1

Verify SSL Inspection Is Enabled

Policy > SSL Inspection

DLP can only inspect decrypted traffic. Before configuring DLP, confirm SSL inspection is active for the users and categories you want to protect.

  • Check that SSL inspection rules exist and are enabled
  • Verify your target user groups are included in the inspection scope
  • Review bypass rules — any bypassed category is invisible to DLP
  • Confirm the intermediate CA certificate is deployed to managed endpoints
SSL Inspection configuration ↗
Step 2

Review Predefined DLP Engines

Administration > DLP > DLP Engines

Zscaler provides predefined engines for common compliance scenarios. You don't need to build anything — just select which engines to activate.

  • Click on Predefined Engines to see the full list
  • Review the PCI engine — detects credit card numbers with Luhn checksum validation
  • Review the PII engine — detects SSNs, names, addresses (High Volume and Low Volume variants)
  • Review the HIPAA engine — detects medical information combined with SSNs
  • Review the Source Code engine — detects programming patterns being uploaded
  • Note which engines are relevant to your organization — you'll reference them when creating rules
DLP Engines overview ↗
Step 3

Create Your First DLP Policy Rule

Policy > Data Loss Prevention

This is where you create the rule that ties an engine to a scope and an action. Start with a single rule in Allow (log only) mode.

  • Click Add DLP Rule
  • Name: "MVP - PCI Monitor" (descriptive name helps with incident review)
  • DLP Engines: Select the PCI engine
  • Action: Select Allow — this logs the incident without blocking anything
  • Users/Groups: Select All Users or start with a specific department
  • Cloud Applications: Leave as "Any" to monitor all destinations
  • File Types: Leave as "All" for maximum visibility
  • Severity: Set based on your org's incident priority model
  • Click Save and Activate Changes

Repeat for PII, HIPAA, and Source Code engines — one rule per engine makes incident review cleaner.

DLP rule configuration ↗
Step 4

Configure Notification Templates

Administration > DLP > Notification Templates

Set up email notifications so the right people are alerted when DLP incidents occur.

  • Click Add Notification Template
  • Auditor Notification: Goes to your security team — include incident details, user info, and destination
  • User Notification: (Optional for Phase 1) Inform the user their action triggered a DLP alert
  • Manager Notification: (Optional) Alert the user's manager for policy violations
  • Assign the notification template to your DLP rules (edit each rule and select the template)
  • Designate a team member or shared mailbox to own the notification inbox
Notification template setup ↗
Step 5

Monitor and Review Incidents

Analytics > Web Insights > DLP

After rules are active, start reviewing the data. This is the most valuable part of Phase 1.

  • Navigate to Analytics > Web Insights and filter by DLP
  • Review incidents by: engine type, user, department, destination, file type
  • Identify false positives — note patterns and tune engine confidence thresholds
  • Identify the top 3-5 riskiest patterns for Phase 3 (Caution) targeting
  • Build a weekly summary: total incidents, top engines triggered, top users, top destinations
Step 6

Graduate to Caution and Block

After 2-4 weeks of monitoring, upgrade validated high-risk rules from Allow to Caution, then eventually Block.

  • Edit your DLP rule and change the action from Allow to Caution
  • Customize the caution page message — explain why the action was flagged
  • Monitor: users who click "Proceed" may need targeted training
  • After validating with Caution (2+ weeks), change to Block for confirmed high-risk rules only
  • Keep Allow rules active for broad monitoring — your DLP program should use all three actions simultaneously
